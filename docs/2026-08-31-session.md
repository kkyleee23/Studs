## The bug we started on

The standing complaint was "the login/signup page cannot fetch data from the
database." Two wrong turns before the answer:

1. **Not email confirmation.** The theory was that with "Confirm email" on,
   `signUp()` returns a user but no session, so `auth.uid()` is null and the
   client-side insert into `public.users` gets rejected by RLS. The project
   reports `mailer_autoconfirm: true` — confirmation is off, signup returns a
   session immediately, and that path worked fine.
2. **It was a paused Supabase project.** Free tier, auto-paused after
   inactivity. Kyle spotted it. A paused project still resolves in DNS, so every
   query fails with a generic network error that looks exactly like a bad key or
   an RLS block. Check this first next time — the CLAUDE.md checklist sends you
   down the wrong path for an hour.

Everything below came out of reading the code, not that bug.

### Crash paths

- `src/data/supabaseClient.js` threw during module evaluation when env vars were
  missing. A throw at static-import time cannot be caught downstream, so one
  missing key took the whole page down with a blank white screen. It now exports
  `configError` and `src/main.js` renders it. It also strips a trailing
  `/rest/v1` off the URL, a shape that has bitten this codebase before.
- `src/main.js` had no error handling around boot at all. It now catches, and
  guards the case where a session exists but the profile row does not.
- New `src/components/errors.js` maps Supabase failures to plain language,
  including the paused-project case.

### Real bugs found

- **Signup fields showed on the sign-in screen.** `[hidden]` had no CSS rule and
  `.field { display: flex }` overrode the attribute. Fixed with a global
  `[hidden] { display: none !important }`.
- **Attendance reported "Saved" when the write failed.** supabase-js returns
  errors rather than throwing, and the old code never checked `error`. It now
  goes through a repo that throws, reverts the control, and shows why.
- Signup had no in-flight state, so double-clicking produced "already
  registered".
- Modals closed on a backdrop click, silently discarding typed input. Both
  `components/modal.js` and the Help dialog in `layout/shell.js` now have an X
  button and ignore backdrop clicks. **Escape-to-close was deliberately not
  added** — Kyle asked for X only.

### Layering

`supabaseClient.js` carried a comment saying UI and services must never import
supabase-js directly. 7 of 8 pages did, plus `shell.js`, and attendance had no
repo or service at all. Now nothing outside `src/data/` touches supabase-js.
Added `usersRepo`, `enrollmentsRepo`, `attendanceRepo`, `enrollmentsService`,
`attendanceService`, `classService.getClass`, and count helpers.

### Database — migration `0007`

At `supabase/migrations/0007_signup_and_rls_hardening.sql` (local only).
**Applied and verified.**

1. **Profile creation moved off the client.** A `handle_new_user` trigger on
   `auth.users` creates the `public.users` row, so it no longer depends on the
   client holding a session. Backfills accounts left without one. Drops
   `users_self_insert`. Skips users with a null email, which would otherwise hit
   `users.email NOT NULL` and fail the entire signup.
2. **Role escalation closed.** `users_self_update` (from `0001`) had
   `USING (id = auth.uid())` and no `WITH CHECK`. Postgres reuses USING as the
   check, so any student could `update users set role_id = 1` to become a
   teacher and then create classes via `classes_teacher_write`. Now has a WITH
   CHECK, and UPDATE is revoked on every column except `full_name` — the column
   privileges are what actually make it airtight, since they are enforced
   independently of RLS.
3. **`public.roles` had RLS off** — the only table in the schema without it.
   Supabase grants anon/authenticated table privileges by default with RLS as
   the gate, so anyone holding the publishable key could rewrite the role lookup
   (`update roles set name='teacher' where id=2` renders the teacher UI for
   every student). RLS on, reads only.

## Traps worth knowing

- **Deleting a row from `public.users` strands the account permanently.** The
  auth row survives, so signup returns "already registered", and the trigger
  only fires on *insert* to `auth.users`, so it never re-runs. The profile has
  to be restored with SQL. The error screen used to advise signing up again; it
  no longer does (`8140136`).
- **`delete from auth.users` can fail on this schema.** `scores.logged_by` and
  `attendance.recorded_by` reference `users(id)` with no ON DELETE clause, and
  `activities.category_id` is ON DELETE RESTRICT. Delete children first, and
  activities before categories. Never delete `public.roles` — the trigger reads
  it.
- **`classes.teacher_id` is ON DELETE CASCADE from `public.users`**, and
  categories, activities, enrollments, scores and attendance cascade from
  classes. One delete on `users` can take out an entire class tree.
- **Vercel:** renaming a project does not move its `.vercel.app` domain, and
  `vercel alias set` creates a *deployment alias* that inherits SSO deployment
  protection — it 302s to a Vercel login page. `studs-web.vercel.app` only
  became public once added as a **project domain**. `vercel project rename`
  exists but is undocumented in `--help`.
- Supabase has two projects on this account. `devbykyle` (org "lame") is the
  portfolio's; Studs is `coqizwfsvkazntybnqrg`. Running Studs SQL against the
  wrong one gives `relation "public.users" does not exist`.
