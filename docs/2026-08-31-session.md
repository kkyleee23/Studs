## The bug we started on

The standing complaint was "the login/signup page cannot fetch data from the database." Two hypotheses were wrong before the real cause turned up:

1. **Email confirmation was NOT the cause.** The theory was that with "Confirm email" on, `signUp()` returns a user but no session, so `auth.uid()` is null and the client-side insert into `public.users` gets rejected by RLS. The project's auth settings report `mailer_autoconfirm: true` — confirmation is off, signup returns a session immediately, and that path worked.
2. **The actual cause was a paused Supabase project.** Free tier, auto-paused after inactivity. Kyle found it and resumed it. A paused project still resolves in DNS, so every query fails with a generic network error that looks exactly like a bad key or an RLS block.

Everything else in this log came out of reading the code, not out of that bug.

## Code changes — commit `84727d1`

**Crash paths**

- `src/data/supabaseClient.js` threw at module evaluation when env vars were missing. A throw during static import cannot be caught downstream, so a missing key took the whole page down with a blank white screen. It now exports `configError` and `src/main.js` renders a real message. It also strips a trailing `/rest/v1` from the URL.
- `src/main.js` had no error handling around boot. It now catches, and guards the case where a session exists but the profile row does not.
- New `src/components/errors.js` maps Supabase failures to plain language, including the paused-project case: *"Can't reach the database right now. It may be paused in your Supabase dashboard, or you may be offline."*

**Real bugs**

- `[hidden]` had no CSS rule, and `.field { display: flex }` overrode the attribute — so the signup-only fields ("Full name", "I am a…") were **visible on the sign-in screen**. Fixed with a global `[hidden]` rule.
- Attendance reported "Saved" even when the write failed. supabase-js returns errors rather than throwing, and the old code never checked `error`. It now goes through a repo that throws, reverts the control, and shows why.
- Signup had no in-flight state, so a double-click produced "User already registered".

**Modals** (requested separately)

- Clicking the backdrop no longer closes a dialog — it silently discarded typed input. Both `components/modal.js` and the Help & tips dialog in `layout/shell.js` got an X button in the header. Cancel still works.
- Escape-to-close was **deliberately not added** — Kyle asked for X only. It is the one standard dialog affordance currently missing.

**Layering**

`supabaseClient.js` carried a comment saying UI and services must never import supabase-js directly. 7 of 8 pages did, plus `shell.js`, and attendance had no repo or service at all. Now no page or service reaches supabase-js: added `usersRepo`, `enrollmentsRepo`, `attendanceRepo`, `enrollmentsService`, `attendanceService`, plus `classService.getClass` and count helpers.

## Database — `supabase/migrations/0007_signup_and_rls_hardening.sql`

**Applied 31 Aug 2026.** Verified: an anon read of `public.roles` now returns
`[]` instead of the three role rows, so RLS is live on that table. The
end-to-end signup path was not re-tested against production.

1. **Profile creation moved off the client.** A `handle_new_user` trigger on `auth.users` creates the `public.users` row, so it no longer depends on the client holding a session. Includes a backfill for accounts left without one. `users_self_insert` is dropped as a result.
2. **Role escalation closed.** `users_self_update` (from 0001) had `USING (id = auth.uid())` and no `WITH CHECK`. Postgres reuses USING as the check, so any student could run `update users set role_id = 1` to become a teacher, then create classes via `classes_teacher_write`. Now has a WITH CHECK, and UPDATE is revoked except on the `full_name` column.
3. **`public.roles` had RLS off** — the only table in the schema without it. Supabase grants anon/authenticated table privileges by default with RLS as the gate, so anyone with the publishable key could rewrite the role lookup (`update roles set name='teacher' where id=2` would render the teacher UI for every student). RLS enabled, reads only.

It was written blind — no psql, Docker, or Supabase CLI on this machine — and applied by Kyle through the Supabase SQL editor.

## Signup verified end to end

All user data was wiped (`auth.users` and every dependent table, leaving
`public.roles` intact) and an account created fresh on studs-web.vercel.app.
Result: straight to the dashboard, sidebar reading "Kyle Sarmiento / Teacher".

That confirms the whole chain — `handle_new_user` fires on insert to
`auth.users`, and it reads both `full_name` and `role` out of
`raw_user_meta_data`, which the client sends via `signUp`'s `options.data`.
Had the metadata not arrived, the name would have fallen back to the email
prefix and the role to student.

Two things learned while getting there:

- Deleting a row from `public.users` strands the account permanently. The auth
  row survives, so signup returns "already registered", and the trigger only
  fires on *insert* to `auth.users`, so it never re-runs. The profile has to be
  restored with SQL. The error screen used to advise signing up again; it no
  longer does (commit `8140136`).
- A plain `delete from auth.users` can fail on this schema.
  `scores.logged_by` and `attendance.recorded_by` reference `users(id)` with no
  ON DELETE clause, and `activities.category_id` is ON DELETE RESTRICT. Children
  have to be deleted first, activities before categories.
